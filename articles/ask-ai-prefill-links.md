note のほうで、マッチングアプリのLPに仕込まれてた「AIに聞く」ボタンの話を書きました。

→ [もっと早く知りたかった！自社LPにAIに営業させる導線を仕込む方法（note）](https://note.com/clever_lion4185/n/nc2acce158402)

そっちは「何が起きてるか」の話なので、こっちには実装だけ書きます。実装、といっても本当にaタグを4本置くだけなので、身構えなくて大丈夫です。

## やることは3つだけ

1. AIに読ませる用の要約ファイルを `llms.txt` として公開する
2. 質問文をURLエンコードして、各AIのチャットURLのクエリに載せる
3. そのリンクをページに置く

サーバーもAPIキーも要りません。静的サイトでも動きます。GitHub Pages でも動きます。

## 各AIのURLには口が空いてる

```
ChatGPT        https://chatgpt.com/?q={encoded}
Claude         https://claude.ai/new?q={encoded}
Perplexity     https://www.perplexity.ai/search?q={encoded}
Google AI Mode https://www.google.com/search?udm=50&q={encoded}
```

4本目が Gemini じゃないのは理由があって、後述します。

おまけでこういうのもあります。

```
# ChatGPT: Web検索を強制する
https://chatgpt.com/?hints=search&q={encoded}

# ChatGPT: 履歴に残さない一時チャット
https://chatgpt.com/?temporary-chat=true&q={encoded}
```

`hints=search` は元ネタのLPでも使われてました。これ地味に大事で、検索が発火しないとAIは llms.txt を読まずに想像で答えてしまいます。効かせられるなら効かせたほうがいいです。

### Gemini だけ効かない

先に書いておきます。**`https://gemini.google.com/app?q=` は効きません。** 私も最初これで組んで、4サービス中1つだけ入力欄が空のまま開くので首をひねりました。

Google はそもそもURLでプロンプトを渡す仕様を出していません。「不安定」ではなく非対応です。これを埋めるためのChrome拡張が複数存在するのが、逆に何よりの証拠だと思います。

で、代わりに使えるのが **Google AI Mode** です。

```
https://www.google.com/search?udm=50&q={encoded}
```

`udm=50` が AI Mode のスイッチです。中身は Gemini なので、答えるモデルは変わりません。しかもこっちの `q=` は普通の検索クエリなので、URLで渡すのが本来の使い方です。確実に通ります。

ただし、これはこれでクセがあります。

**改行が保持されません。** `q=` はあくまで検索クエリなので `%0A` が落ちます。何が起きるかというと、

```
次の記事を読んでください。
https://example.com/article
この記事の内容が…
```

これがそのまま送られると、

```
…読んでください。 https://example.com/articleこの記事の内容が…
```

**URLの末尾に次の行が直結します。** URLが壊れて記事を読みに行けなくなる場合があるので、AI Mode に渡すときは改行を空白に潰しておく必要があります。

```javascript
const flat = prompt.replace(/[ \t]*\n+[ \t]*/g, " ").trim();
```

**「まず質問して」も効きません。** AI Mode は対話ではなく1ターンの検索応答なので、質問を返さずいきなり要約を出してきます。後述の「プロンプトが本体」で書く設計は、ここでは成立しません。

なので使い分けとしてはこうなります。

| | 対話させたい（質問を返させる） | 1発で答えさせたい |
|---|---|---|
| ChatGPT / Claude | ◯ | ◯ |
| Perplexity | △ | ◯ |
| Google AI Mode | ✕ | ◯ |

型Aの説得型（「なぜ最適なのか教えて」）なら AI Mode でも成立します。型Bや対話型を狙うなら、AI Mode は数合わせで並べるだけになります。

:::message alert
これらは各社が「仕様です」と公開してるものではないので、全部予告なく変わります。本番に置くなら、たまに自分で踏んで確認する運用が要ります。実際この記事も、下書きの時点では Gemini を4本目に入れてました。
:::

## エンコードで詰む話

```javascript
const prompt = `次の記事を読んでください。
${articleUrl}

この記事の内容が私の職場に当てはまるかを確認したいです。
いきなり結論を出さず、まず私の業種・職種・組織規模について5つ質問してください。`;

const url = `https://claude.ai/new?q=${encodeURIComponent(prompt)}`;
```

改行はコード上で `\n` を使えば `%0A` になって渡ります。元ネタも `%0A%0A` で段落を分けてました。

Python なら。

```python
import urllib.parse
url = "https://claude.ai/new?q=" + urllib.parse.quote(prompt)
```

で、ここが本題なんですが、**URL全体で2000文字を超えると環境によって切り捨てられます。**

日本語がクセモノで、エンコードすると1文字が9文字に膨らみます（`あ` → `%E3%81%82`、3バイト × 3文字）。体感よりずっと早く上限に当たる。日本語200字でだいたい1800字です。ちょっとした指示文でもう限界です。

つまり **データそのものは載せられません。** 載せられるのはURLと短い指示だけ。これが設計上いちばん効いてくる制約なので、先に頭に入れておいてください。

## 読ませるファイルを作る（llms.txt）

プリフィルにデータを載せられない以上、AIに読ませる材料は公開URLとして置くことになります。そこで `llms.txt` です。

規約自体はシンプルで、サイトのルートに Markdown を置くだけ。

```
/llms.txt        サイト全体の目次と要約
/llms-full.txt   全ページを展開した完全版
```

元ネタのやつを見ると、`llms-full.txt` は各ページを `<page>` タグで区切って、YAML frontmatter に `title` / `description` / `source_url` を持たせた構造でした。

```markdown
<page>
---
title: "..."
description: "..."
source_url:
  html: https://example.com/faq
  md: https://example.com/faq.md
---

## よくある質問
Q: ...
A: ...
</page>
```

技術的には何も難しくないです。難しいのは中身のほうで、**何をどれだけ書くかが、そのままAIの回答の傾向になります。**

元ネタのマッチングアプリだと「安全性」と「解約方法」のFAQが異様に厚くて、それはそのまま離脱要因への反論処理でした。つまり llms.txt は技術ファイルの顔をしたコンテンツ設計です。置けば効くもんではないです。

## 2つの型があった

その後もう1件見つけたので、設計の違いを書いておきます。

### 型A: 説得型（記事末・LP下部に静置）

固定の質問文を1本だけ持って、サービスの評価をAIに語らせるやつ。

```
NewMatch が私にとってなぜ最適な選択肢なのか、その理由を教えて下さい。
（＋ トップページ・llms.txt・llms-full.txt のURL）
```

「最適かどうか」ではなく「なぜ最適なのか」。前提が入った聞き方です。実装はいちばん簡単で、静的なリンク4本で終わります。

### 型B: 見積型（常時表示のFAB＋モーダル）

条件をスロットとして埋めさせて、AIを検索・見積のフロントエンドとして使うやつ。

```
{サービス名}（{ドメイン}）で候補を出してください。
エリア：{エリア}
予算：{予算}
```

デジタルサイネージ広告の掲載枠を扱うサービスがこの形でした。エリアと予算を入れると、AIが該当する媒体を価格順にズラッと並べて返してきます。正直これは便利です。

で、**型Bが成立する条件は「料金表を機械可読で公開してること」**です。広告媒体の値段って普通「お問い合わせください」の裏に隠すものですが、それを llms.txt 側に出したから、AIが在庫を7件並べて相場観まで返せてる。

裏返すと、価格や在庫を出したくないサービスは型Bを採れません。型Aで止まります。ここが分岐点かなと思います。

## プロンプトが本体

技術的な難しさはゼロですが、効くかどうかはここでほぼ決まります。

### やりがちで効かないやつ

```
この記事を要約して {url}
```

読み終わった人に要約を出しても価値ゼロです。押されません。

### 効くやつ

読者自身の状況につなげるプロンプト。

```
次の記事を読んでください。
{url}

この記事の手法を私の業務に合わせて具体化したいです。
まず私の職種と、いま時間を取られている作業について質問してから提案してください。
```

コツは **「まず質問して」を入れること**です。これがあると一方通行の回答じゃなくて対話が始まるので、記事の続きが読者ごとに生成される状態になります。

型Bをやるなら、スロットは2つまでに絞るのが現実的だと思います。元ネタもエリアと予算の2つだけでした。3つ以上になると、AIに渡す前にフォームを埋める作業が発生して、ボタンの手軽さが消えます。

## 貼る場所ごとの制約

### note

**任意のHTMLが置けません。** テキストリンクになります。

- 本文に「ChatGPTに聞く」と打つ
- その文字を選択して、リンク挿入でURLを貼る

URLをそのまま貼り付けるとカード化されてしまうので、必ず文字を選択してから貼ります。見た目はボタンになりませんが、機能は同じです。

### Zenn / GitHub / Obsidian

Markdown がそのまま使えます。

```markdown
[ChatGPTに聞く](https://chatgpt.com/?q=...)
```

### 自前サイト

HTML。`target="_blank"` と `rel="noopener"` を付けます。

## ジェネレータ作った

記事ごとにプロンプトを変えると、毎回エンコードするのがダルいです。なので記事URLと質問文を入れたら4サービス分のリンクを吐くやつを作りました。

- プリセットのプロンプト（自分の状況に当てはめる / 実務に落とす / 反論させる / など）
- `{url}` プレースホルダの置換
- note / Markdown / HTML の3形式で書き出し
- URL長のカウント（2000字超で警告）
- 生成されるURLの構造を色分け表示
- Gemini は既定でオフ（選ぶと非対応の警告が出ます）
- AI Mode 向けだけ改行を空白に自動変換

→ **[「AIに聞く」リンクジェネレータ](https://kake-nami.github.io/zenn-content/tools/ask-ai-link-generator.html)**（ソース: [ask-ai-link-generator.html](https://github.com/kake-nami/zenn-content/blob/main/tools/ask-ai-link-generator.html)）

HTML1枚です。外部通信もビルドも要らないので、保存すればオフラインでも動きます。入力した質問文もブラウザの外に出ません。

![リンクジェネレータの画面。記事URLと質問文を入れると、生成されたURLがベースURL・クエリパラメータ・エンコードされた質問文の3色に分かれて表示される。サービス欄では Gemini に「プリフィル非対応」のバッジが付いている](/images/ask-ai/generator.png)
*URLの構造を色分けして出してます。上のメーターは最長URLの文字数で、2000字に近づくと色が変わる。Gemini は既定でオフ、AI Mode には改行が落ちる旨の注記が出ます*

コアはこれだけです。

```javascript
const SERVICES = [
  { name: "ChatGPT",        base: "https://chatgpt.com/?q=" },
  { name: "Google AI Mode", base: "https://www.google.com/search?udm=50&q=" },
  { name: "Claude",         base: "https://claude.ai/new?q=" },
  { name: "Perplexity",     base: "https://www.perplexity.ai/search?q=" },
];

const build = (prompt, articleUrl) =>
  SERVICES.map(s => ({
    label: `${s.name}に聞く`,
    url: s.base + encodeURIComponent(prompt.replaceAll("{url}", articleUrl)),
  }));
```

生成したリンクを実際に踏むとこうなります。

![生成したリンクを踏んだ直後の画面。プロンプトが展開された状態で送信され、AIが記事を読んだうえで5つの質問を返している](/images/ask-ai/prefilled-result.png)
*「まず質問して」が効いて、回答じゃなく質問から始まってる。冒頭の「記事は問題なく読むことができました」は、プロンプト末尾に入れた「読めなかった場合はその旨を」への返事*

## ハマりどころ

**AIがURLを読みに行くとは限らない**

Web検索・取得が無効な状態だと、記事を読まずに想像で答えます。存在しない内容を堂々と要約されるので、なかなか厄介です。プロンプトに「読めなかった場合はその旨を答えてください」を入れておくと多少マシになります。

**有料記事は読めない**

いろんな記事の有料部分は当然取得できません。無料部分だけで答えられます。

**読めないサイトがある**

最近多いですね。そういったやつのURLを渡しても読めないです。

**パラメータ仕様が変わる**

さっきも書きましたが、各社の都合で予告なく変わります。公開前と、公開後もたまに踏んで確認します。

## 「AI流入が増えた」は本当か

最後にこれだけ書いておきたいです。いちばん注意が要るところだと思ってます。

この手の話でよく「AI経由の流入が増えた」という報告を見るんですが、ちょっと待ってほしくて。

**このボタンは、自サイトの訪問者をChatGPTへ送り出す仕組みです。**

ということは、そこから戻ってきた分もリファラは `chatgpt.com` になります。つまり自分で送り出したお客さんが帰ってきてるだけでも、指標の上では「AI流入の増加」に見えてしまう。

これ、自分の尻尾を数えてるだけの可能性があるんですね。

切り分けるには最低限これが要ります。

- ボタンのクリック数を計測する（ボタン側に独自イベントを置く）
- リンクに流入元の識別子を付ける（元ネタのApp Storeリンクには `ct=llms_txt` みたいなのが入ってました）
- `chatgpt.com` からの着地数と、ボタンのクリック数を突き合わせて差分を見る

差分がプラスなら、ボタンを踏んでない人がAI経由で来てる＝純粋な新規獲得です。ここを見ないまま効果を語ると、たぶん後で困ります。

## まとめ

- 実装コストはほぼゼロ。aタグ4本
- 効くかどうかは、プリフィルするプロンプトと llms.txt の中身で決まる
- 型Bを採れるかは、価格や在庫を機械可読で出せるかで決まる
- URL長の制約で、データではなくURLしか渡せない。つまり **AIに読ませたいものは公開URLとして持っている必要がある**

最後のやつ、地味ですが構造的な話だと思ってます。自分のプロダクトのデータをAIに評価させたいなら、そのデータが公開URLで取れる形で存在してるかどうかが最初の分岐になる。ここができてないと、そもそも型Bの土俵に上がれません。

私も別で＊＊＊の＊＊＊を＊＊＊するものを作ってるんですが、同じ壁に当たりました。その話はまた別途。
