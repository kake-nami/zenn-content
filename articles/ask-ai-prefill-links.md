自社サイトに「ChatGPTに聞く」「Claudeに聞く」ボタンを置く実装の話です。

実例を2件分解したうえで、自分のブログに移植し、リンク生成ツールまで作ったところまで書きます。

なぜその実例が面白いのか、という考察のほうは note に分けました。実装だけ知りたい人はこの記事で完結します。

→ [もっと早く知りたかった！自社LPにAIに営業させる導線を仕込む方法（note）](https://note.com/clever_lion4185/n/nc2acce158402)

## 全体像

やることは3つだけです。

1. AIに読ませる用の要約ファイルを `llms.txt` として公開する
2. 質問文をURLエンコードして、各AIのチャットURLのクエリに載せる
3. そのリンクをページに置く

サーバーもAPIキーも要りません。静的サイトでも動きます。

## 1. 各サービスのプリフィルURL

```
ChatGPT     https://chatgpt.com/?q={encoded}
Claude      https://claude.ai/new?q={encoded}
Perplexity  https://www.perplexity.ai/search?q={encoded}
Gemini      https://gemini.google.com/app?q={encoded}
```

オプションでこういうものもあります。

```
# ChatGPT: Web検索を強制する
https://chatgpt.com/?hints=search&q={encoded}

# ChatGPT: 履歴に残さない一時チャット
https://chatgpt.com/?temporary-chat=true&q={encoded}
```

`hints=search` は実例でも使われていました。llms.txt を読ませたい場合、検索・取得が発火しないと質問文だけで答えられてしまうので、効かせられるなら効かせたほうがいいパラメータです。

:::message alert
**Gemini の `?q=` はプリフィルが不安定です。** 効く時期と効かない時期があります。また、これらは各社が仕様として公開しているものではないので、予告なく変わります。本番に置くなら定期的に踏んで確認する運用が必要です。
:::

## 2. エンコード

```javascript
const prompt = `次の記事を読んでください。
${articleUrl}

この記事の内容が私の職場に当てはまるかを確認したいです。
いきなり結論を出さず、まず私の業種・職種・組織規模について5つ質問してください。`;

const url = `https://claude.ai/new?q=${encodeURIComponent(prompt)}`;
```

改行はコード上で `\n` を使えば、エンコード後に `%0A` になって渡ります。

Python なら:

```python
import urllib.parse
url = "https://claude.ai/new?q=" + urllib.parse.quote(prompt)
```

**URL全体で2000文字を超えると環境によって切り捨てられます。** 日本語はエンコードで1文字あたり9文字（`%E3%81%82` = 3バイト × 3文字）に膨らむので、体感よりずっと早く上限に当たります。日本語200字でだいたい1800字です。

つまり**データそのものは載せられません**。載せられるのはURLと短い指示だけ。これが設計上いちばん効く制約です。

## 3. 読ませるものを用意する（llms.txt）

プリフィルにデータを載せられない以上、AIに読ませる材料は公開URLとして置くことになります。そこで `llms.txt` です。

規約自体は単純で、サイトルートに Markdown を置くだけ。

```
/llms.txt        サイト全体の目次と要約
/llms-full.txt   全ページを展開した完全版
```

実例のものを見ると、`llms-full.txt` は各ページを `<page>` タグで区切り、YAML frontmatter に `title` / `description` / `source_url` を持たせた構造でした。

```markdown
<page>
---
title: "..."
description: "..."
source_url:
  html: https://example.com/faq
  md: https://example.com/faq.md
---

## よくある質問
Q: ...
A: ...
</page>
```

**中身の配分がそのまま回答の傾向になります。** マッチングアプリの例では「安全性」と「解約方法」のFAQが突出して厚く、それはそのままユーザーの離脱要因への反論処理でした。

llms.txt はSEOでいうところのコンテンツ設計に相当します。置けば効くものではなく、何をどれだけ書くかが全部です。

## 4. 2つの型

実例を2件見つけたので、設計の違いを整理しておきます。

### 型A: 説得型（記事末・LP下部に静置）

固定の質問文を1本だけ持ち、サービスの評価をAIに語らせる形。

```
NewMatch が私にとってなぜ最適な選択肢なのか、その理由を教えて下さい。
（＋ トップページ・llms.txt・llms-full.txt のURL）
```

「最適かどうか」ではなく「なぜ最適なのか」。前提を含んだ聞き方になっています。実装は最も簡単で、静的なリンク4本で終わります。

### 型B: 見積型（常時表示のFAB＋モーダル）

条件をスロットとして埋めさせ、AIを検索・見積のフロントエンドとして使う形。

```
{サービス名}（{ドメイン}）で候補を出してください。
エリア：{エリア}
予算：{予算}
```

デジタルサイネージ広告の掲載枠を扱うサービスがこの形でした。エリアと予算を入れるとAIが該当する媒体を価格順に並べて返してきます。

**型Bが成立する条件は「料金表を機械可読で公開していること」です。** 広告媒体の価格は普通「お問い合わせ」の裏に隠すものですが、それを llms.txt 側に出したから、AIが在庫を7件並べて相場観まで返せている。

裏返すと、価格や在庫を出したくないサービスは型Bを採れません。型Aで止まります。

## 5. プロンプト設計

技術的な難しさはゼロですが、効果はここでほぼ決まります。

### やりがちで効かないもの

```
この記事を要約して {url}
```

記事を読み終わった人にとって、要約の価値はゼロです。押されません。

### 効くもの

読者自身の状況に接続するプロンプト。

```
次の記事を読んでください。
{url}

この記事の手法を私の業務に合わせて具体化したいです。
まず私の職種と、いま時間を取られている作業について質問してから提案してください。
```

ポイントは **「まず質問して」を入れること**です。これがあると一方通行の回答ではなく対話が始まり、記事の続きが読者ごとに生成される状態になります。

型Bを採るなら、スロットは2つまでに絞るのが現実的です。実例もエリアと予算の2つだけでした。3つ以上になると、AIに渡す前にフォームを埋める作業が発生して、ボタンの手軽さが消えます。

## 6. 掲載先ごとの制約

### note

任意のHTMLを置けません。テキストリンクになります。

- 本文に「ChatGPTに聞く」と打つ
- その文字を選択して、リンク挿入でURLを貼る

URLを直接貼り付けるとカード化されてしまうので、必ず文字を選択してから貼ります。

### Zenn / GitHub / Obsidian

Markdown がそのまま使えます。

```markdown
[ChatGPTに聞く](https://chatgpt.com/?q=...)
```

### 自前サイト

HTML。`target="_blank"` と `rel="noopener"` を付けます。

## 7. ジェネレータ

記事ごとにプロンプトを変えると、毎回エンコードするのが面倒になります。記事URLと質問文を入れると4サービス分のリンクを吐くツールを作りました。

- プリセットのプロンプト（自分の状況に当てはめる / 実務に落とす / 反論させる / など）
- `{url}` プレースホルダの置換
- note / Markdown / HTML の3形式で書き出し
- URL長のカウント（2000字超で警告）
- 生成されるURLの構造を色分け表示

→ **[「AIに聞く」リンクジェネレータ](https://kake-nami.github.io/zenn-content/tools/ask-ai-link-generator.html)**（ソース: [ask-ai-link-generator.html](https://github.com/kake-nami/zenn-content/blob/main/tools/ask-ai-link-generator.html)）

単一のHTMLファイルで、外部通信もビルドも不要です。保存すればオフラインでも動きます。入力した質問文はブラウザの外に出ません。

コアの部分はこれだけです。

```javascript
const SERVICES = [
  { name: "ChatGPT",    base: "https://chatgpt.com/?q=" },
  { name: "Gemini",     base: "https://gemini.google.com/app?q=" },
  { name: "Claude",     base: "https://claude.ai/new?q=" },
  { name: "Perplexity", base: "https://www.perplexity.ai/search?q=" },
];

const build = (prompt, articleUrl) =>
  SERVICES.map(s => ({
    label: `${s.name}に聞く`,
    url: s.base + encodeURIComponent(prompt.replaceAll("{url}", articleUrl)),
  }));
```

## 8. 落とし穴

**AIがURLを読みに行くとは限らない**
Web検索・取得が無効な状態だと、記事を読まずに想像で答えます。存在しない内容を要約されるリスクがあるので、プロンプトに「読めなかった場合はその旨を答えてください」を入れておくと多少マシになります。

**有料記事は読めない**
note の有料部分は当然取得できません。無料部分だけで答えられます。

**パラメータ仕様が変わる**
各社の都合で予告なく変わります。公開前と、公開後もたまに踏んで確認します。

**「AI経由の流入が増えた」は自己循環かもしれない**

これがいちばん注意が要る点です。

このボタンは、**自サイトの訪問者をChatGPTへ送り出す**仕組みです。そこから戻ってきた分もリファラは `chatgpt.com` になります。つまり自分で送り出した客が帰ってきているだけでも、指標上は「AI流入の増加」に見える。

切り分けるには最低限これが要ります。

- ボタンのクリック数を計測する（ボタン側に `utm` ではなく独自イベントを置く）
- リンクに識別子を付ける（例: App Storeリンクの `ct=llms_txt` のような流入元パラメータ）
- `chatgpt.com` からの着地数と、ボタンのクリック数を突き合わせて差分を見る

差分がプラスなら、ボタンを踏んでいない人がAI経由で来ている＝純粋な新規獲得です。ここを見ないまま「AI流入が増えた」と言うと、自分の尻尾を数えることになります。

## まとめ

- 実装コストはほぼゼロ。aタグ4本
- 効果を決めるのは、プリフィルするプロンプトと、読ませる llms.txt の中身
- 型Bを採れるかは、価格や在庫を機械可読で公開できるかで決まる
- URL長の制約により、データではなくURLしか渡せない。つまり**AIに読ませたいものは公開URLとして持っている必要がある**

最後の点は、AI前提でサービスを設計するときの構造的な要求だと思っています。自分のプロダクトのデータをAIに評価させたいなら、そのデータが公開URLで取得可能な形で存在しているかどうかが最初の分岐になります。
